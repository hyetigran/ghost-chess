- **#13 — server-side move validation**: `supabase/functions/submit-move/index.ts` — a Deno edge function that is now the *only* path that writes to `games`/`moves`; it authenticates the caller, rate-limits (`move_attempts` table, 30 attempts/60s), fetches the true game row, decides legality via chess.js, and — if legal — calls the `apply_move` RPC (`supabase/schemas/06_functions.sql`), which atomically inserts the move and updates the game in one transaction so `sync_player_views` never observes one write without the other. Every illegal-move reason (not a participant, not your turn, game not active, chess.js rejects it) returns the identical `{ error: "illegal_move" }` response via the same code path (ADR-0007) — auth/rate-limit responses are allowed to differ since they don't disclose board state (a nonexistent gameId is folded into the uniform illegal_move response too, not given its own 404 — that would disclose which game IDs are real). `apply_move` is locked down to `service_role` only (`revoke execute ... from public`) — a client calling it directly would bypass all validation. The move-legality decision is mirrored as a Jest-tested pure function at `src/lib/game/decide-move.ts` (13 tests) — same dual-implementation pattern as `redact_fen`/`redact-fen.ts`, since the edge function runs in an isolated Deno runtime and can't cleanly share a file with the RN app's module graph. This also gives `games.is_check` its first real writer. Client wiring: `src/api/server/game.ts`'s old `makeMove` replaced with `submitMove` (calls the edge function, returns no game state per ADR-0001 — callers read the result from `player_views`).
- **#12 — client reads no longer leak true game state**: `player_views` gained `white_player_id`/`black_player_id` columns (not secret — CONTEXT.md's Visibility is about piece positions, not opponent identity — but the client needs *some* way to know who it's playing without reading `games` directly). `games`/`moves` SELECT RLS restricted to non-`active` status (the one status with real secrets); `waiting` and `completed`/`abandoned` stay directly readable, which is what lets `createGame`'s post-insert `.select()` keep working without changes. `src/api/server/game.ts`'s `getGame` reads `player_views` instead of `games` — the only client read path for game state now, full stop, not just while active. `GameScreen`, `useGameTimer`, and the move-mutation's optimistic-update logic consume `PlayerView` instead of `Game` (`redacted_fen` instead of `fen`, no `pgn` field). Verified live through the real client library: a real JWT-authenticated read confirms a participant gets their own redacted row with both player IDs, a direct `games` SELECT during `active` returns nothing, and a non-participant's `player_views` read for a game they're not in returns nothing.
- **#12's code-review fix-up, since superseded by the #13 merge (see below)**: #12 was branched from `main` before #13 merged, so its RLS tightening above broke #13's *pre-merge* direct-write path too (the original `makeMove`, before #13 existed, did `.from('moves').insert(...)` / `.from('games').update(...)` directly) — Postgres denies a row to `UPDATE` (and to any RLS subquery reading it) unless it *also* passes the table's own SELECT policy, independent of the UPDATE/INSERT policy's own USING/WITH CHECK, so an `active`-only SELECT restriction silently broke every direct write to an `active` game. #12 fixed this at the time with two `security definer` RPCs: `is_game_participant(game_id)` (used by `moves`' INSERT policy instead of a raw subquery) and `submit_own_move`/`end_own_game` (doing the actual writes after checking participancy themselves). Also fixed in the same pass: `src/api/server/user.ts`'s `getActiveGames`, never audited in #12's original pass despite selecting `fen` directly from `games` — repointed at `player_views` instead (same pattern as `getGame`), with `ActiveGame`/`activeGameSchema` now derived from `PlayerView`.
- **Merging #12 and #13 together (this pass)**: `submit_own_move` is gone — #13's `submit-move` edge function + `apply_move` RPC is the real, validated write path now, and once it exists, `submit_own_move` isn't just redundant, it's a *bypass*: a security-definer RPC that let a participant insert an arbitrary move + fen with no chess-legality checking at all (only turn-ownership), directly contradicting ARCHITECTURE.md's "there is exactly one validation path" invariant. `src/api/server/game.ts`'s `makeMove` is gone too, superseded by `submitMove`. `moves` now has **no INSERT policy at all** — with RLS enabled and no policy for a command, Postgres denies it outright, which is exactly right: the only legitimate writer is `apply_move`, itself `security definer` and `service_role`-locked, so the old moves INSERT policy was never protecting anything for that path — its only real effect, once `submit_own_move` is gone, would have been letting a client bypass `apply_move` entirely via a direct REST insert. `is_game_participant` is gone too (was only ever called by the now-deleted policy). Also dropped: `games`' `"Users can update their own games"` policy — the "known issue" below (from #12) noted `endGame` relied on this broad UPDATE access, but that's no longer true now that `endGame` goes through `end_own_game`, and a `grep` across `src/` for any remaining direct `.from('games').update(...)` call found none — so, same reasoning as the moves policy, this was a live bypass (a client could rewrite `fen`/`status`/`result`/`winner_id`/clocks directly, no validation at all) with zero remaining legitimate use. `end_own_game` **stays** — #13 doesn't touch resignation, so `endGame` still needs the RPC #12 built for the same games-SELECT-gates-UPDATE reason, just for a different write. New migration drops both policies and both functions.
- **#14 — per-move deadline enforcement**: `gameSettingsSchema.timeControl`(minutes)/`timeIncrement`(seconds) replaced with `timeControlHours: 1|12|24` — the old shape was a cumulative Fischer clock, the exact model ADR-0006 rejected. `white_time_remaining`/`black_time_remaining` dropped entirely from `games` and `player_views`: under per-move deadlines there's only ever one relevant countdown (whoever's turn it is), fully derived from `updated_at` (already set to `now()` on every accepted move — no new column needed as the turn-start anchor) plus the time control, so there was nothing to persist. `player_views` gained `time_control_hours` (denormalized from `games.settings`, same reasoning as `white_player_id`/`black_player_id`) since the client needs it and must never read `games` directly. New pure module `src/lib/game/deadline.ts` (`deadlineFor`/`isDeadlineLapsed`/`secondsUntilDeadline`, 8 Jest tests) is the readable reference, mirrored inline in `submit-move`'s Deno runtime and in a scheduled Postgres function (same dual-implementation pattern as `redact_fen`/`decide-move`). Two enforcement layers: `decide-move.ts`/`submit-move` fold "has the mover's own deadline lapsed" into the same uniform illegal-move rejection as every other reason (ADR-0007) — this is what stops a move sneaking through in the gap between a deadline lapsing and the sweep below catching it; a `pg_cron` job (`forfeit_lapsed_games()`, every minute) sweeps every `active` game past its deadline and forfeits it, which is the layer that doesn't depend on any client being open (the actual point of the ticket — a scheduled check, not just a reactive one). `apply_move`'s signature lost its two time-remaining params (dropped a whole class of state to keep in sync, not just renamed).
  - **New `timeout` result value, not reused `abandoned`**: surfaced a real domain question (asked and resolved via user input) — should a lapsed-deadline forfeit share `abandoned` with resignation, or get its own value? Went with distinct, because investigating it surfaced a genuine pre-existing bug: `update_ratings_after_game`'s `'abandoned'` branch derived the loser from `current_turn` (mirroring checkmate's logic), which is only correct when the loser and the player-to-move are the same — true for a timeout, **not** true for a resignation (a player can resign on either turn). This silently computed the wrong winner and wrong ELO delta for any resignation that happened on the resigner's own turn, ever since `end_own_game` (#12) started correctly setting `winner_id` itself — the trigger was overwriting it with a wrong value derived from `current_turn`. Fixed by having the `'abandoned'` branch trust `new.winner_id` (already correct) and giving `'timeout'` its own branch that *does* derive from `current_turn` (correctly, for that case). Verified live with the actual bug scenario: black resigns while `current_turn = 'white'` — old logic would have credited black (the resigner) as the winner; fixed logic correctly credits white. CONTEXT.md gained a Forfeit glossary entry documenting the distinction.

- **#15 — Realtime subscriptions to `player_views`**: `useGameSubscription` (`src/lib/hooks/use-game-subscription.ts`) opens a `postgres_changes` channel filtered by `game_id`, writing incoming rows straight into the same TanStack Query cache key (`['game', gameId]`) `gameQueries.gameById` uses — additive to the existing one-shot fetch, not a replacement (still need an initial value before the first Realtime event, and `useMakeMove`'s `onSettled` refetch stays as a fallback). `supabase/schemas/08_realtime.sql` adds `player_views` to the `supabase_realtime` publication; `games` is deliberately never added. Safe to filter by `game_id` alone (matches both players' rows for that game) because Realtime authorizes each change against the subscriber's own SELECT RLS before delivery — verified live with a real control, not just "non-participant received nothing" (which the code-review Spec pass correctly pointed out doesn't by itself rule out the channel just never having warmed up, see the debugging note below): the **same client/session**, subscribed to two games at once under identical warm-up — one where they're a real participant (control), one where they're not — with both games mutated in the same instant. The control game's channel fired, the non-participant game's didn't. Since it's the same pipe, same session, same moment, RLS is the only thing that can explain the difference.
  - **Debugging note for next time this needs touching**: local Realtime (`postgres_changes` via `wal2json`) has a real, reproducible warm-up gap between the client receiving `SUBSCRIBED` and the server-side WAL consumer actually watching that specific filter — subscribe-then-immediately-mutate reliably missed the event in testing (even for a service-role subscriber with no RLS involved), while the identical setup with a ~2-5s pause after `SUBSCRIBED` worked every time, with real delivery latency around 300ms once warmed up (comfortably inside PRD §3.4's <500ms target). Doesn't matter for real usage (a player opening a game screen has no reason to move within milliseconds of subscribing under an hours-long per-move deadline), but matters for writing a reliable test against local Realtime.

  - **Code-review fix-up, and a much bigger finding underneath it**: the Spec pass caught that the original "own capture, detected directly" design was built on a false premise — it checked whether the target square was occupied in the *pre-move* `redacted_fen` and assumed an occupied square could only mean a real capture (since chess.js "never offers a friendly-occupied square as a legal target").   - **That investigation surfaced an even more severe, separate bug**: the same "opponent pieces are structurally absent, not just hidden" fact means chess.js's own legal-move generation, run locally against a redacted FEN (#17's legal-move highlighting), **silently omits a pawn's diagonal capture entirely** whenever the piece there is hidden — a pawn can only move diagonally when chess.js can see something to capture, and against a redacted board it never can. Verified directly: `chess.moves({square:'e4', verbose:true})` against a redacted position with a real, invisible enemy pawn on d5 returns only `['e5']` — d5 never appears. Since `useSquareSelection`'s tap-to-move flow only accepts moves inside `legalTargets`, this meant **a player could not capture a hidden enemy piece with a pawn at all** through the UI — not a cosmetic gap, a block on the single most central mechanic in a game about capturing hidden pieces. Non-pawn pieces were unaffected (a knight/bishop/rook/queen can always move to an empty-looking square regardless of capture status, so those moves were still offered and still worked — just, per the bug above, without ever registering as a "capture" client-side). ## Known issues / debt

- **Verified against a live local Supabase/Postgres instance**: migration applies cleanly, redaction/atomic-sync/capture-aggregation/reveal-on-completion/RLS isolation all confirmed correct by hand — own-row-only visibility holds for both players and for a non-participant, captures are shared to both rows, full true FEN appears on both rows once `status` reaches a terminal state (`completed`/`abandoned` — deliberately excludes the pre-game `waiting` status ADR-0003 didn't anticipate; see that ADR's file for why).
- **`on_auth_user_created` trigger, missing from migrations since the beginning (#32, fixed)**: `handle_new_user()` and this trigger were both defined in `supabase/schemas/06_functions.sql` from the start, but only the function itself made it into the initial migration — the `CREATE TRIGGER` was never captured, confirmed via `pg_trigger` against a fresh instance (no trigger existed on `auth.users` at all). Fixed with a new migration (`20260801090000_add_auth_user_created_trigger.sql`) that adds the trigger. Wiring the trigger up for real surfaced a second bug that was invisible while the trigger didn't exist: `handle_new_user()` read `username` straight from `raw_user_meta_data`, but Anonymous Auth (`src/api/auth/index.ts`'s `signInAnonymously`, ADR-0005) — the only signup path this app actually has today, since there's no `supabase.auth.signUp()` call anywhere in the codebase yet — only ever sets `device_id` there, never `username`. With the trigger correctly wired, every anonymous sign-in would otherwise violate `users.username`'s `NOT NULL` constraint and roll back the *entire* signup (the trigger runs inside the same transaction as the `auth.users` insert). Fixed by falling back to `'guest_' || replace(new.id::text, '-', '')` when metadata has no `username` — derived from `id`, so it can't collide with `username`'s `UNIQUE` constraint the way a counter or short random suffix could. Verified live: a real anonymous sign-in now produces a matching `public.users` row with a generated guest handle, and a hand-inserted `auth.users` row with an explicit `username` in metadata still respects that value (the `coalesce` fallback only applies when metadata omits it). Also did the drift audit the issue asked for (tables, functions, triggers, policies — schema files' final state vs. everything ever `CREATE`d across migrations): this trigger was the only real drift found.
- `redact_fen`'s en-passant handling always hides the target square rather than reasoning about whether the viewer could legally see it — deliberate simplification (see the function's doc comment), not a bug, but worth knowing if extending it.
- `is_check` now has a real writer (`supabase/functions/submit-move`, via `apply_move`).
- `supabase/config.toml` had `enable_anonymous_sign_ins = false` — flipped to `true` while testing #13, since guests can't sign in at all otherwise. This wasn't a #13-specific bug, it's a real config gap that would've blocked every guest on a fresh deploy; fixed here rather than filed separately since it's a one-line config flag, not code.
- Rate limiting (`move_attempts`, 30/60s) and the atomic `apply_move` RPC's grants both hit the same default-privileges trap ticket #11 found for `player_views`: Postgres only grants `service_role` DELETE/REFERENCES/TRIGGER by default on a `postgres`-owned table (not SELECT/INSERT), and EXECUTE on new functions defaults to PUBLIC. Both needed explicit grants — verified live (an insert into `move_attempts` silently returned no error but wrote nothing until fixed; a `set role authenticated` call to `apply_move` was confirmed rejected with "permission denied").
- The `move_attempts` rate limit is keyed only on `auth.uid()`. Since this same ticket enables anonymous sign-ins, an attacker can in principle mint fresh anonymous sessions to reset the 30/60s counter. Not fixed here: Supabase's own auth layer already throttles anonymous sign-ins independently (`supabase/config.toml`'s `[auth.rate_limit] anonymous_users = 30` per hour per IP), so the realistic ceiling is bounded, not unlimited, even without IP-level tracking in `submit-move` itself. Worth a dedicated hardening pass (e.g. IP-based limiting in the edge function) if abuse is ever observed, but ADR-0007 only asks for *a* per-user limit, which this satisfies.
- Time controls reaching 0 now forfeits the game (#14) — see the dedicated bullet above.
- **`/code-review` on PR #34 (CodeRabbit) surfaced several genuinely serious findings, not nitpicks — all fixed and re-verified live**:
  - `ILLEGAL_MOVE_RESPONSE` was a module-scope singleton `Response`. Response bodies are single-use, and Deno's production runtime reuses the isolate across requests (unlike the local `supabase functions serve --no-verify-jwt` dev server's "oneshot" policy, which re-evaluates the module per request) — this would have thrown "body already consumed" on the second illegal-move rejection in production. Local testing structurally could not have caught this. Converted to a factory function.
  - TOCTOU race: the edge function reads `games.fen`, decides legality, then calls `apply_move` in a separate step — two near-simultaneous submissions could both validate against the same fen before either commits. Fixed with optimistic concurrency: `apply_move` now takes `p_expected_fen` and makes the `games` update conditional on it (`where id = ... and fen = p_expected_fen`), raising `stale_precondition` if zero rows match; `move_number` is now computed inside the same transaction from `public.moves` rather than trusted from a separately-run count query, closing the same race for it. Added a `unique (game_id, move_number)` constraint on `moves` as a hard backstop. Verified directly at the SQL level (two `apply_move` calls with the same `p_expected_fen`: first succeeds, second raises `stale_precondition`) rather than relying on an HTTP-level race that the local dev server might not actually interleave.
  - Threefold repetition was undetectable: `new Chess(fen)` has no move history, and chess.js needs the actual move sequence (not just a snapshot) to track repeated positions. `GameSnapshot` gained a `moveHistory: string[]` field; both `decide-move.ts` and the edge function now reconstruct the `Chess` instance by replaying SAN history from the start (falling back to loading `fen` directly when history is empty — equivalent for a real fresh game, and what lets existing hand-constructed endgame-study test fixtures keep working without needing a realistic move sequence). Verified both via a unit test and a real 8-half-move knight-shuffle game played through the actual edge function.
  - `gameId` wasn't validated as a UUID — a malformed value made the `move_attempts` insert fail silently (only logged, not handled), so a caller who always sent a malformed `gameId` would never increment their own rate-limit counter. Added UUID-shape validation alongside the existing `from`/`to` checks.

  - `ChessBoard.onMove` never passed `promotion`, so every pawn-promotion attempt silently failed as an unexplained illegal move (chess.js requires `promotion` for that case).
