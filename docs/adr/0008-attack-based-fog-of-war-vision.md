# Attack-based Fog of War vision replaces absolute occlusion

Ghost Chess originally hid every opponent piece unconditionally, for the whole active game (see [ADR-0001](./0001-server-side-redaction.md), [ADR-0002](./0002-shadow-table-for-redacted-views.md)) — a player's `redacted_fen` never showed an opponent piece under any circumstance. The product direction changed to a real Fog of War model: a player should see an opponent piece the moment one of their own pieces genuinely threatens it, not just at capture.

We decided visibility is computed per move as "does one of the viewer's own pieces currently attack this square" — sliding pieces (bishop/rook/queen) reveal a ray up to and including the first blocker, pawns reveal only their two diagonal capture squares (never the square directly ahead), knights and the king reveal their normal one-step-or-jump reach. This is deliberately the same geometry a piece's *attack* squares always were, computed against the true board, independent of whose turn it is or any move-legality question ([ADR-0009](./0009-king-capture-ends-the-game.md) covers legality separately) — vision is a pure read of the current position, not a simulation of what could happen next. There is no persistence: a piece that leaves the viewer's vision goes dark again immediately, with no "remembered" trace carried in `redacted_fen` — matching the letter of the rule ("currently attacks") and avoiding a second kind of hidden-state staleness bug on top of the first.

The redaction function itself (`redact_fen`, `supabase/schemas/08_functions.sql`) still runs inside `sync_player_views`, in the same transaction as every move, per ADR-0002 — only the piece-visibility predicate changed, not where or when it's enforced. The TS reference mirror (`src/lib/game/redact-fen.ts`) uses chess.js's public `isAttacked()`; the SQL enforcement point has no chess-movement primitive available anywhere in Postgres, so it's a from-scratch hand-rolled board-parse-and-ray-walk, cross-checked against the TS version's output on shared fixtures rather than trusted by inspection alone. The client (`ChessBoard`'s fog tint) recomputes the same vision set locally from its own already-redacted FEN rather than receiving new data from the server — a piece that's the first blocker on one of the viewer's own rays is, by construction, always already revealed in that same redacted view, so the client-computed set is provably identical to what the server computed from the true board.

We rejected a fixed-radius "N squares around your pieces" model (simpler to compute, but has no chess meaning — it would reveal pieces a player couldn't actually do anything about, and hide ones they could) and a persistent "fog of war memory" of previously-seen squares (the user's own confirmed intent was "currently attacks," not "ever attacked," and persistence would reopen exactly the kind of hidden-state-staleness risk ADR-0001/0002 exist to close, plus new leak-surface questions about whether stale memory could ever mislead a player into a false sense of certainty). We also explicitly reject ever exposing vision as its own queryable endpoint ("can I currently see square X?") — [ADR-0007](./0007-constant-time-move-rejection.md)'s "no two-step server exchange" principle applies here just as much as it does to move legality: vision must ship exclusively through the existing `player_views` redacted-state read/subscription path, never a new interactive oracle a client could probe repeatedly.
